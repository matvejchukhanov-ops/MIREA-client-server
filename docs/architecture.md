# Архитектура

Документ описывает устройство сервера и клиента: из каких частей они состоят,
как обслуживаются несколько клиентов одновременно, где хранятся данные и что
происходит при сбоях.

---

## 1. Общая схема

```
   ┌────────────┐                     ┌───────────────────────────────────────────┐
   │ Клиент №1  │──── TCP :9000 ─────▶│                  Сервер                   │
   └────────────┘                     │  главный поток: accept()                  │
   ┌────────────┐                     │        │                                  │
   │ Клиент №2  │──── TCP :9000 ─────▶│   поток 1   поток 2   …   поток N         │
   └────────────┘                     │        └───────┬───────────┘              │
                                      │                ▼                          │
                                      │   протокол → диспетчер → обработчики      │
                                      │     (вход, аудит)           │             │
                                      │                ┌────────────┴─────────┐   │
                                      │                ▼                      ▼   │
                                      │       файловая часть (fs/)      база (db/)│
                                      └──────────────┬───────────────────────┬────┘
                                                     ▼                       ▼
                                          storage/user-<id>/       data/filemanager.db
```

Задание допускает консольное или клиент-серверное приложение. Выбрана
клиент-серверная схема: она делает границу доверия явной. Всё, что пришло из
сокета, проверяется сервером, а клиент — лишь удобная оболочка, которую
атакующий может заменить своей.

## 2. Слои

```
   server/main.py            аргументы командной строки, запуск
        │
   server/tcp_server.py      слушающий сокет, accept, поток на клиента
        │
   server/connection.py      фрейминг, цикл запрос-ответ одного клиента
        │
   server/protocol.py        разбор JSON-запроса, сборка ответа, коды ошибок
        │
   server/dispatcher.py      поиск команды, проверка входа, журнал аудита
        │
   server/handlers.py        команды: связывают запрос с fs/, db/, auth/
        │
   ┌────┴─────────────┬───────────────────┐
   server/fs/         server/db/          server/auth/
   песочница,         SQLite: схема,      scrypt, вход,
   файлы, JSON/XML,   пользователи,       регистрация
   ZIP, диски         реестр, журналы
```

Зависимости направлены сверху вниз. Пакеты `fs/`, `db/`, `auth/` не знают о
сети и протоколе: функции принимают пути и данные, возвращают результат или
бросают исключение. Поэтому разбор пути, распаковка архива или правила входа
проверяются тестами без сокетов.

| Модуль | Ответственность |
|---|---|
| `server/app.py` | Сборка долгоживущих объектов: база, хранилище, сервис входа |
| `server/session.py` | Состояние соединения: кто вошёл, счётчик неудачных входов |
| `server/fs/sandbox.py` | Путь клиента → путь на диске, защита от обхода каталогов |
| `server/fs/manager.py` | Чтение, атомарная запись, удаление, каталоги, листинг |
| `server/fs/locks.py` | Блокировки по пути |
| `server/fs/formats.py` | Безопасные JSON и XML |
| `server/fs/archive.py` | Упаковка и проверяемая распаковка ZIP |
| `server/fs/drives.py` | Список дисков (WinAPI на Windows, `/proc/mounts` на Linux) |
| `server/db/schema.sql` | Таблицы, ограничения, триггеры журнала |
| `server/db/repository.py` | Все SQL-запросы — подготовленные выражения |
| `server/auth/passwords.py` | Хеширование и правила для логина и пароля |
| `server/auth/service.py` | Регистрация, вход, блокировка |

Соответствие рекомендуемой архитектуре из задания:

| В задании | Здесь |
|---|---|
| Модуль управления файлами | `fs/manager.py`, `fs/sandbox.py`, `fs/locks.py` |
| Модуль обработки JSON/XML | `fs/formats.py` |
| Модуль архивации | `fs/archive.py` |
| Модуль интеграции с БД | `db/` |
| Аутентификация и контроль доступа | `auth/`, проверка входа в `dispatcher.py` |
| Журнал аудита | таблица `audit_log`, запись в `dispatcher.py` |

## 3. Путь одного запроса

```
  {"cmd":"write","path":"docs/a.txt","content":"..."}\n
        │
        ▼  connection.py     FrameReader выделяет кадр по \n
        ▼  protocol.py       JSON → Request; проверка типов полей
        ▼  dispatcher.py     команда существует? нужен вход — он есть?
        ▼  handlers.write    достаёт аргументы, вызывает fs/
        ▼  fs/sandbox.py     "docs/a.txt" → storage/user-7/docs/a.txt (проверено)
        ▼  fs/manager.py     блокировка пути → временный файл → os.replace
        ▼  db/repository.py  INSERT/UPDATE files → триггер пишет operations
        ▼  dispatcher.py     INSERT audit_log (успех или код ошибки)
        ▼  protocol.py       {"status":"ok","result":{...}}\n
```

Ошибка на любом шаге становится ответом с кодом: `FsError` переводится в
`ProtocolError` декоратором `translate_errors`, а непредвиденное исключение —
в `INTERNAL_ERROR` с трассировкой в логе сервера. Соединение при этом живо.

## 4. Хранилище

```
storage/
├── user-1/        каталог пользователя с id = 1
│   ├── docs/
│   └── notes.txt
└── user-2/
data/
└── filemanager.db
```

- Каталог пользователя создаётся при регистрации и называется по id из базы,
  а не по логину.
- Временные файлы атомарной записи и распаковки называются `.fm-tmp-*`, лежат
  рядом с целевым файлом (так `os.replace` атомарен) и скрыты из листинга.
  Клиент не может создать файл с таким именем.

Устройство базы — [database.md](database.md).

## 5. Конкурентность

### Поток на клиента

`accept()` и `recv()` блокирующие: в одном потоке сервер, разговаривая с одним
клиентом, не вернулся бы к `accept()`. Главный поток только принимает
подключения, на каждое создаётся фоновый поток, живущий столько же, сколько
соединение. Не больше 64 одновременно — лишний клиент получает `SERVER_BUSY`.

### Что разделяется между потоками

| Объект | Как защищён |
|---|---|
| Счётчик активных соединений | `threading.Lock` |
| Диспетчер, конфигурация | Только чтение после запуска |
| База данных | Соединение на операцию; `BEGIN IMMEDIATE` упорядочивает запись; WAL |
| Файлы на диске | Блокировки по пути (`fs/locks.py`), атомарная замена |
| Сессия, буфер чтения | Локальны в потоке — синхронизация не нужна |

Подробно о гонках и их устранении — [security.md](security.md#8-состояния-гонки).

### Путь масштабирования

Для тысяч клиентов вместо потоков применялся бы `asyncio`. Смена модели
затронула бы `tcp_server.py` и `connection.py`; протокол, диспетчер и пакеты
`fs/`, `db/`, `auth/` остались бы без изменений.

## 6. Жизненный цикл сервера

1. Сборка `Services`: создание каталога хранилища, файла базы и схемы
   (повторный запуск схему не трогает — `CREATE ... IF NOT EXISTS`).
2. Создание сокета, флаг повторного использования адреса — `SO_EXCLUSIVEADDRUSE`
   на Windows, `SO_REUSEADDR` на POSIX. На Windows `SO_REUSEADDR` позволил бы
   чужому процессу перехватывать подключения.
3. `bind`, `listen`, цикл `accept()` с таймаутом опроса 0,5 с — иначе `Ctrl+C`
   на Windows не прерывал бы ожидание.
4. На каждое подключение — поток или отказ `SERVER_BUSY`.
5. Остановка: закрыть слушающий сокет, дать потокам до 2 секунд завершиться.

## 7. Обработка ошибок

| Что произошло | Последствие |
|---|---|
| Ошибка в данных клиента (путь, формат, нет файла) | Ответ с кодом, соединение живо |
| Некорректный JSON | `BAD_JSON`, соединение живо |
| Превышен размер кадра | `FRAME_TOO_LONG`, корректное закрытие соединения |
| Пять неудачных входов в соединении | `AUTH_FAILED`, затем закрытие |
| Клиент оборвал связь | Поток завершается, сокет освобождается |
| Таймаут бездействия | Соединение закрывается |
| Непредвиденное исключение в обработчике | `INTERNAL_ERROR`, трассировка в логе, соединение живо |
| Сбой записи в журнал аудита | Команда выполнена, ответ отправлен, сбой — в лог сервера |
| Не удалось создать хранилище или базу при запуске | Сообщение и код возврата 1 |

## 8. Клиент

| Модуль | Ответственность |
|---|---|
| `client/main.py` | Аргументы, цикл ввода, запрос пароля, подтверждение перезаписи |
| `client/commands.py` | Строка пользователя → запрос протокола |
| `client/render.py` | Ответ сервера → текст для человека |
| `client/connection.py` | Подключение, фрейминг, отправка и приём |

Пароль запрашивается отдельно через `getpass` и не отображается. Многострочный
текст вводится до строки из одной точки. Клиент ничего не проверяет за сервер —
разве что JSON перед отправкой, чтобы подсказать опечатку раньше.

## 10. Логирование

| Уровень | Что попадает |
|---|---|
| `INFO` | Запуск, путь хранилища и базы, подключения и отключения |
| `WARNING` | Нарушения протокола, превышение пределов |
| `ERROR` | Непредвиденные исключения с трассировкой |
| `DEBUG` | Кадры запросов и ответов: до 300 байт, пароль замаскирован |

Лог сервера — технический. Журнал действий пользователей — в базе
(`audit_log`), его видно командой `log`.
