# Программа и методика испытаний

Документ описывает, что и как проверяется в системе, и приводит результаты
последнего прогона.

---

## 1. Объект и цели испытаний

**Объект:** клиент-серверный файловый менеджер с базой данных SQLite.

**Цели:**

1. Подтвердить выполнение функциональных требований задания: диски, операции
   с файлами, JSON и XML, ZIP, база данных, журнал действий.
2. Воспроизвести каждую атаку из [security.md](security.md) и убедиться, что
   она отражена: SQL-инъекция, обход каталогов, XXE, «миллиард смеющихся»,
   Zip Slip, zip-бомба, небезопасная десериализация, состояния гонки, подбор
   пароля.
3. Убедиться, что ошибка клиента не разрывает соединение и не роняет сервер.
4. Убедиться, что несколько клиентов работают одновременно, не мешая друг
   другу и не получая доступа к чужим файлам.

---

## 2. Средства и порядок проведения

| Параметр | Значение |
|---|---|
| Инструмент | `unittest` из стандартной библиотеки Python |
| Дополнительные пакеты | не требуются |
| Команда запуска | `python -m unittest discover` |
| Каталог | корень проекта |
| Предварительный запуск сервера | не требуется |

Каждый тест, которому нужны файлы или база, получает свой временный каталог
и удаляет его по завершении (`tests/support.py`). Интеграционные тесты
поднимают сервер в отдельном потоке на свободном порту. Тесты не трогают
`storage/` и `data/` и не мешают запущенному вручную серверу.

```bash
python -m unittest tests.test_archive        # один набор
python -m unittest discover -v               # с именами проверок
```

## 3. Уровни тестирования

| Уровень | Наборы | Что проверяется |
|---|---|---|
| Модульный | `test_framing`, `test_protocol`, `test_sandbox`, `test_auth`, `test_database`, `test_files`, `test_formats`, `test_archive`, `test_drives`, `test_dispatcher`, `test_client` | Компоненты по отдельности, без сети |
| Компонентный | `test_commands` | Команды сервера целиком — обработчики, база, хранилище — без сокетов |
| Интеграционный | `test_integration` | Система через реальные TCP-сокеты |

Модульный уровень возможен благодаря разделению на слои: пакеты `fs/`, `db/`,
`auth/` не зависят от сети, поэтому атака на распаковку архива проверяется
вызовом функции, без сервера.

## 5. Методика по требованиям задания

| Требование задания | Как проверяется | Тесты |
|---|---|---|
| 1. Список дисков и свойства ФС | Хотя бы один диск; все поля на месте; свободное ≤ общего, доступное ≤ свободного | `test_drives` |
| 2. Чтение, запись, удаление файлов | Создание, перезапись только с флагом, удаление, ошибки при отсутствии | `test_files.ReadWriteTests`, `DeleteAndDirectoryTests` |
| 3. JSON и XML | Запись и чтение туда-обратно с совпадением; отказ на опасных документах | `test_formats`, `test_commands.FileCommandTests` |
| 4. ZIP | Упаковка каталогов, просмотр, распаковка с совпадением содержимого | `test_archive.RoundTripTests` |
| 5. База данных | Таблицы из задания; реестр файлов; операции create/modify/delete пишутся триггерами | `test_database.SchemaTests`, `OperationTriggerTests` |
| 6. Журнал действий | Успешные и неуспешные команды, попытки без входа; пароль не попадает; журнал не стирается | `test_dispatcher.AuditTests`, `test_database.ImmutabilityTests`, `test_commands` |
| Аутентификация с хешированием | scrypt с солью, проверка, блокировка | `test_auth` |
| Подготовленные выражения | Инъекции в логине и пути остаются данными; статический разбор исходника запросов | `test_database.InjectionTests` |
| Ограничение размера при распаковке | Zip-бомба по сжатию, по суммарному размеру, по ложному заголовку | `test_archive.AttackTests` |
| Минимальное доверие при десериализации | Только примитивы, дубликаты ключей, NaN, глубина | `test_formats.JsonTests` |
| Race conditions | 8 потоков создают один файл — ровно один успех; читатель не видит недописанный файл; параллельные счётчики не теряют приращений | `test_files.RaceTests`, `test_database.ConcurrencyTests`, `test_integration.ConcurrencyTests` |

### Как воспроизводятся атаки

| Атака | Входные данные теста | Ожидаемый результат |
|---|---|---|
| SQL-инъекция | Логин `x' OR '1'='1`, путь `a'); DROP TABLE users; --` | Пользователь не найден; таблица на месте; путь сохранён как есть |
| Path traversal | 17 вариантов: `../`, `C:\`, `\\server\share`, `a.txt\x00.jpg`, `a.txt:hidden`, `CON`, `a.txt.` и др. | `BAD_PATH` |
| Обход по префиксу | Каталог `user-10` рядом с `user-1` | Не считается вложенным |
| XXE | `<!ENTITY x SYSTEM "file:///etc/passwd">`, `SYSTEM "http://169.254.169.254/"` | `BAD_FORMAT`, файл не записан |
| «Миллиард смеющихся» | Девять уровней сущностей по десять ссылок | `BAD_FORMAT` до разворачивания |
| Zip Slip | `../../evil.txt`, `/tmp/evil.txt`, `C:/Windows/evil.txt`, `..\..\evil.txt` | `UNSAFE_ARCHIVE`, ничего не распаковано, временный каталог удалён |
| Zip-бомба | Мегабайт нулей (сжатие ~1000×); архив больше предела; заголовок с ложным размером | `UNSAFE_ARCHIVE` или `BAD_ARCHIVE` |
| Ссылка в архиве | Запись с режимом `0o120777` | `UNSAFE_ARCHIVE` |
| Подбор пароля | 5 неверных паролей | Блокировка учётной записи; разрыв соединения |
| Выяснение логинов | Время входа с несуществующим логином | Не меньше 30 % от времени с существующим |
| Стирание следов | `DELETE FROM audit_log`, `UPDATE operations`, `UPDATE files SET owner_id` | `IntegrityError` от триггера |
| Глубокий JSON в запросе | 100 000 вложенных скобок | `BAD_JSON`, а не обрыв соединения |

## 7. Дефекты, выявленные испытаниями

### Дефект 1. Пароль в отладочном логе

**Проявление.** При запуске с `--log-level DEBUG` в лог попадали сырые кадры
запросов — и с ними пароль при каждом `login` и `register`.

**Причина.** Отладочный вывод кадров достался от предыдущей версии протокола,
в которой секретов не было.

**Устранение.** Значение поля `password` заменяется на `***` до записи в лог;
кадр обрезается до 300 байт.

**Значение.** Хеширование паролей в базе бессмысленно, если открытый пароль
лежит в текстовом файле рядом.

### Дефект 2. Кадр не вмещал файл предельного размера

**Проявление.** Интеграционный тест записи файла из управляющих символов
получил `FRAME_TOO_LONG` и потерял соединение.

**Причина.** JSON записывает управляющий символ шестью байтами (`\u0001`).
Файл, который сервер разрешал записать, не помещался в кадр ответа.

**Устранение.** Конфигурация проверяет при запуске, что кадр не меньше
`6 × размер файла + 16 КБ`; сервер с несогласованными пределами не стартует.

### Дефект 3. Искажение кириллицы при вводе из файла

**Проявление.** Сценарий проверки, поданный клиенту через канал, записывал
на сервер текст в двойной кодировке.

**Причина.** При перенаправленном вводе Python в Windows читает stdin в
кодировке системы (cp1251), а сценарий был в UTF-8.

**Устранение.** Клиент переключает stdin на UTF-8, если ввод не из консоли.

### Дефект 4. Ошибки в самих тестах

- Тест времени входа блокировал учётную запись собственными попытками и получал
  `ACCOUNT_LOCKED` вместо `AUTH_FAILED` — для замера использован отдельный
  сервис входа с высоким пределом.
- Тест зашифрованной записи не срабатывал: `zipfile` сбрасывает флаг шифрования
  при записи. Флаг выставляется правкой байтов готового архива.

## 8. Не покрытое автоматическими тестами

| Область | Способ проверки |
|---|---|
| Интерактивный ввод пароля без отображения | Запуск клиента в консоли |
| Прерывание сервера по `Ctrl+C` | Запуск и остановка |
| Работа по локальной сети | `--host 0.0.0.0`, подключение с другой машины |
| Таймаут бездействия | Требует ожидания 300 секунд |
| Снятие блокировки учётной записи по времени | Требует ожидания 5 минут |
| Список дисков с пустым DVD или картридером | Нужен такой привод |

Сценарий ручной проверки — пример сеанса в [user-guide.md](user-guide.md#пример-сеанса).
