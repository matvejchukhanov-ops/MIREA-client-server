# Пояснительная записка

**Дисциплина:** Разработка безопасного программного обеспечения

**Работа:** Семестровое задание № 1

**Тема:** разработка файлового менеджера с использованием базы данных

**Репозиторий:** https://github.com/matvejchukhanov-ops/MIREA-client-server

---

## Аннотация

Разработано клиент-серверное приложение — файловый менеджер, который работает
с текстовыми файлами, документами JSON и XML и архивами ZIP, показывает
сведения о дисках сервера и хранит пользователей, реестр файлов и журналы
действий в реляционной базе данных SQLite.

Основное содержание работы — защита от типовых уязвимостей: SQL-инъекций,
обхода каталогов, небезопасной десериализации, XXE, zip-бомб и Zip Slip,
состояний гонки, подбора паролей. Для каждой угрозы приведены механизм
защиты и автоматический тест, воспроизводящий атаку.

Объём: 4477 строк кода в 33 модулях и 161 строка схемы базы данных;
2268 строк тестов, 241 автоматический тест. Внешних зависимостей нет —
приложение работает на стандартной библиотеке Python.

## 1. Введение

### 1.1 Постановка задачи

Требуется создать консольное или клиент-серверное приложение, способное
эффективно управлять файлами разного формата (текстовые, JSON, XML, ZIP) и
обеспечивающее высокий уровень безопасности, включая работу с реляционной
базой данных.

Функциональные требования задания:

1. Получение списка дисков и свойств файловой системы.
2. Чтение, запись и удаление файлов.
3. Хранение и чтение данных в JSON и XML.
4. Создание и извлечение ZIP-архивов.
5. Хранение информации о файлах и операциях с ними в базе данных.
6. Журнал активности пользователей в базе данных.

### 1.2 Цель

Разработать приложение, которое выполняет перечисленные функции и остаётся
корректным при любых входных данных: ни путь, ни имя записи в архиве, ни
содержимое документа, присланные пользователем, не должны дать ему больше,
чем разрешено.

### 1.3 Задачи

1. Составить модель угроз и для каждой угрозы выбрать механизм защиты.
2. Спроектировать схему базы данных по образцу из задания.
3. Реализовать файловые операции в изолированном каталоге пользователя.
4. Реализовать безопасный разбор JSON и XML и проверяемую распаковку ZIP.
5. Реализовать аутентификацию с хешированием паролей и контроль доступа.
6. Реализовать журнал аудита, который нельзя незаметно изменить.
7. Устранить состояния гонки при одновременной работе клиентов.
8. Воспроизвести каждую атаку автоматическим тестом.

### 1.4 Выбор архитектуры и средств

**Клиент-сервер, а не консольное приложение.** В консольном приложении
пользователь и программа находятся по одну сторону границы доверия. В
клиент-серверном граница проходит по сокету: всё, что пришло из сети,
проверяется сервером, а клиент можно заменить любой программой. Это делает
требования безопасности осмысленными — атакующий действительно может прислать
`../../etc/passwd` в обход интерфейса.

**Python вместо C#.** Теоретическая часть задания написана для .NET, но язык
не регламентирован. Использован Python 3.11+: стандартная библиотека
содержит всё необходимое — `sqlite3`, `zipfile`, `json`, `xml.parsers.expat`,
`hashlib.scrypt`, — и приложение запускается без установки пакетов, в том
числе на Astra Linux в аудитории. Соответствие классов .NET из теоретической
части и средств Python:

| .NET (System.IO и др.) | Python | Где используется |
|---|---|---|
| `DriveInfo.GetDrives()` | WinAPI через `ctypes`; `/proc/mounts` + `os.statvfs` | `fs/drives.py` |
| `Directory`, `DirectoryInfo` | `pathlib.Path`, `os.scandir` | `fs/manager.py` |
| `File`, `FileInfo`, `FileStream` | `open`, `os.fstat`, `os.replace` | `fs/manager.py` |
| `System.Text.Json.JsonSerializer` | `json` | `fs/formats.py` |
| `XDocument`, LINQ to XML | `xml.parsers.expat`, `ElementTree` | `fs/formats.py` |
| `ZipFile`, `ZipArchive` | `zipfile` | `fs/archive.py` |
| `BinaryFormatter` | `pickle` — **сознательно не используется** | — |

**SQLite.** Задание допускает PostgreSQL, MySQL или SQLite. SQLite не требует
отдельного сервера — база является одним файлом. Отсутствие хранимых процедур
компенсировано триггерами (§3.3).

## 2. Анализ угроз

Активы: файловая система сервера вне хранилища, файлы пользователей, учётные
данные, журналы, доступность сервера. Нарушители: сетевой клиент без учётной
записи, вошедший пользователь, другой пользователь того же сервера, владелец
украденной копии базы.

| Угроза | Источник | Механизм защиты |
|---|---|---|
| SQL-инъекция | Логин, путь | Подготовленные выражения; статическая проверка исходника |
| Обход каталогов | Путь, имя записи архива | Разбор на компоненты + сверка после `resolve()` |
| Небезопасная десериализация | Содержимое JSON | Только JSON → примитивы; дубликаты ключей, NaN, глубина |
| XXE, «миллиард смеющихся» | Содержимое XML | Запрет DTD до разворачивания сущностей |
| Zip Slip, zip-бомба | Архив | Проверка имён, пределы размера и сжатия, счёт байт |
| Состояния гонки | Параллельные клиенты | Блокировки путей, атомарная замена, атомарные SQL-приращения |
| Подбор пароля | `login` | scrypt, блокировка учётной записи, разрыв соединения |
| Обход проверки входа | Любая команда | Запрет по умолчанию в диспетчере |
| Сокрытие следов | Доступ к базе | Триггеры, запрещающие правку журналов |
| Отказ в обслуживании | Любые данные | Пределы на кадр, файл, соединения, вложенность |

Подробный разбор каждой угрозы — [security.md](security.md).

## 3. Проектирование

### 3.1 Общая архитектура

Сервер принимает подключения по TCP, обслуживает каждого клиента в отдельном
потоке и хранит файлы пользователей в каталогах `storage/user-<id>/`, а
сведения о пользователях, файлах и действиях — в базе `data/filemanager.db`.
Клиент — консольное приложение.

Сервер разделён на слои: транспорт (`tcp_server`, `connection`), протокол,
диспетчер (контроль доступа и аудит), обработчики команд и три пакета без
зависимости от сети — `fs/` (файлы), `db/` (база), `auth/` (вход). Соответствие
рекомендуемой архитектуре задания:

| Модуль из задания | Реализация |
|---|---|
| Модуль управления файлами (CRUD) | `fs/manager.py`, `fs/sandbox.py`, `fs/locks.py` |
| Модуль обработки JSON/XML | `fs/formats.py` |
| Модуль архивации с ограничением размера | `fs/archive.py` |
| Модуль интеграции с БД (подготовленные выражения, процедуры) | `db/repository.py`, `db/schema.sql` |
| Аутентификация и контроль доступа | `auth/`, `dispatcher.py` |
| Журнал аудита | `audit_log`, `dispatcher.py` |

Подробно — [architecture.md](architecture.md), диаграммы — [diagrams.md](diagrams.md).

### 3.2 Прикладной протокол

Сообщения — объекты JSON, одно сообщение — одна строка (TCP не сохраняет
границ сообщений, поэтому они задаются разделителем). 23 команды, 27 кодов
ошибок. Ошибка в данных клиента возвращается кодом и не разрывает соединение.
Спецификация — [protocol.md](protocol.md).

### 3.3 База данных

Таблицы `users`, `files`, `operations` повторяют вариант из задания; добавлена
таблица `audit_log` — журнал активности.

| Отличие от примера задания | Причина |
|---|---|
| `ENUM` → `TEXT CHECK (... IN ('create','modify','delete'))` | В SQLite нет ENUM |
| Хранимые процедуры → триггеры | В SQLite нет процедур |
| `files.deleted_at` вместо удаления строки | На файл ссылается журнал операций |
| `users.failed_logins`, `locked_until` | Блокировка при подборе пароля |

Смысл хранимых процедур — правило выполняется в базе и не зависит от того,
вспомнило ли о нём приложение. Это свойство дают триггеры:

- **журнал операций ведёт база.** Приложение меняет только `files`; запись
  в `operations` создают триггеры на `INSERT` и `UPDATE`. Изменить файл без
  записи в журнал нельзя даже ручным SQL-запросом;
- **история неизменяема.** Триггеры запрещают `UPDATE` и `DELETE` для
  `operations` и `audit_log`, удаление записей о файлах и смену их владельца.

Схема и обоснование — [database.md](database.md).

## 4. Реализация

### 4.1 Диски и файловая система (требование 1)

Стандартная библиотека Python не перечисляет диски и не сообщает тип файловой
системы. На Windows используются функции WinAPI `GetLogicalDrives`,
`GetDriveTypeW`, `GetVolumeInformationW`, `GetDiskFreeSpaceExW` — те же, что
лежат под `DriveInfo` в .NET; на Linux — `/proc/mounts`, `/dev/disk/by-label`,
`os.statvfs`. Ответ содержит те же сведения, что `DriveInfo`: имя, тип,
файловая система, метка, готовность, объём, свободное место всего и доступное
пользователю. Перед опросом устройств выключается системный диалог «Вставьте
диск» — иначе пустой картридер подвесил бы поток сервера.

### 4.2 Операции с файлами (требование 2)

Каждый путь от клиента проходит песочницу (`fs/sandbox.py`): разбор на
компоненты с отказом на `..`, абсолютных путях, буквах дисков, нулевом байте,
двоеточии (потоки NTFS), именах устройств Windows, завершающих точках; затем
`resolve()` и проверка, что результат лежит внутри каталога пользователя.

Запись выполняется атомарно: во временный файл в том же каталоге, `fsync`,
`os.replace`. Проверка существования и запись — под одной блокировкой пути.
Размер читаемого файла проверяется у открытого дескриптора (`fstat`), а не по
пути до открытия. Удаляются только файлы, а каталоги — только пустые:
рекурсивное удаление одной командой стоило бы слишком дорого при опечатке.

### 4.3 JSON и XML (требование 3)

JSON разбирается модулем `json`, который создаёт только словари, списки и
примитивы, — в отличие от `pickle` и `BinaryFormatter`, выбор класса объекта
файлу недоступен. Дополнительно отвергаются повторяющиеся ключи, `NaN`,
`Infinity` и вложенность глубже 32 уровней.

XML разбирается напрямую через `expat` с обработчиками, прерывающими разбор
на первом объявлении DTD или сущности. Этим закрыты XXE и «миллиард
смеющихся». Результат — дерево из словарей `{tag, attrs, text, children}`,
которое сразу передаётся клиенту в JSON. Документ с DTD не записывается на
диск: `xml_write` пропускает текст через тот же разбор. Сборка XML из дерева
идёт через ElementTree с экранированием.

### 4.4 ZIP-архивы (требование 4)

Упаковка — рекурсивно по каталогам, без перехода по символическим ссылкам.
Распаковка проходит две фазы. Сначала проверяются все заголовки: число записей,
имена (те же правила, что для путей — защита от Zip Slip), шифрование,
символические ссылки, дубликаты без учёта регистра, суммарный размер и степень
сжатия каждой записи (защита от zip-бомб). Затем — распаковка во временный
каталог со счётом фактически записанных байт: заголовки пишет создатель
архива, и верить им нельзя. После успеха временный каталог переименовывается
в целевой, при неудаче удаляется целиком.

### 4.5 База данных и журнал операций (требование 5)

Все запросы — подготовленные выражения с параметрами `?`. Тест разбирает
исходник модуля запросов синтаксическим анализатором Python и проверяет, что
текст SQL нигде не собирается из переменных — новый запрос с f-строкой
провалит тест.

Соединение с базой открывается на каждую операцию (объект соединения `sqlite3`
нельзя делить между потоками), транзакции записи начинаются с
`BEGIN IMMEDIATE`, журнал базы — в режиме WAL. Файлы, распакованные из архива,
регистрируются одной транзакцией.

### 4.6 Аутентификация и журнал активности (требование 6)

Пароли хешируются `scrypt` с солью; параметры хранятся рядом с хешем.
Сравнение — `hmac.compare_digest`. Для несуществующего логина хеш тоже
вычисляется, и ответ одинаков — по ответу и времени нельзя узнать, какие
логины есть. После пяти неудачных попыток подряд учётная запись блокируется
на 5 минут; после пяти неудачных попыток в одном соединении оно закрывается.

Проверка входа и запись в журнал сделаны в диспетчере, а не в обработчиках.
Команда закрыта, пока при регистрации её явно не объявили открытой, — забыть
проверку невозможно. Журнал `audit_log` получает каждую команду: пользователя,
адрес, команду, объект, успех и код ошибки. Пароль и содержимое файлов в журнал
не попадают; в отладочном логе сервера пароль маскируется.

### 4.7 Устранение состояний гонки

| Гонка | Решение |
|---|---|
| Два клиента создают один файл | Проверка и запись под блокировкой пути |
| Чтение недописанного файла | Атомарная замена `os.replace` |
| Подмена файла между проверкой и открытием | `fstat` по открытому дескриптору |
| Параллельные неудачные входы теряют приращения | `failed_logins = failed_logins + 1` в SQL |
| Два клиента регистрируют один логин | Ограничение `UNIQUE` в базе |
| Взаимная блокировка при упаковке | Захват замков в отсортированном порядке |

### 4.8 Кроссплатформенные особенности

- Флаг повторного использования порта: `SO_EXCLUSIVEADDRUSE` на Windows,
  `SO_REUSEADDR` на POSIX — на Windows `SO_REUSEADDR` позволил бы чужому
  процессу перехватывать подключения.
- Windows не даёт заменить файл, открытый другим потоком; замена повторяется
  до 20 раз с паузой 25 мс.
- Имена устройств (`CON`, `NUL`), завершающие точки и потоки NTFS опасны
  только на Windows, но отвергаются везде: клиент может работать на одной
  системе, а сервер — на другой.
- Вывод и перенаправленный ввод переключаются на UTF-8: иначе Windows
  использует кодировку системы.

## 5. Тестирование

241 автоматический тест на `unittest` трёх уровней: модульные (компоненты без
сети), компонентные (команды сервера без сокетов), интеграционные (реальный TCP).
Каждая атака из §2 воспроизведена тестом: 17 вариантов обхода каталогов,
XXE с чтением файла и запросом в сеть, «миллиард смеющихся», четыре варианта
Zip Slip, три вида zip-бомб, инъекции в логине и пути, восемь потоков,
одновременно создающих один файл.

При испытаниях найдены и устранены три дефекта программы: пароль в отладочном
логе, несогласованность пределов кадра и файла, искажение кириллицы при
перенаправленном вводе. Программа и методика — [testing.md](testing.md).

## 7. Заключение

Поставленная задача выполнена: разработан клиент-серверный файловый менеджер,
выполняющий все шесть функциональных требований задания и хранящий данные в
реляционной базе.

Итоговая цель курса — умение разрабатывать надёжные приложения, работающие с
базой данных и файлами разного формата, осознавая риски и справляясь с
уязвимостями вроде SQL-инъекций и состояний гонки. В работе это выразилось
в следующем:

1. **Граница доверия проведена явно.** Сервер проверяет каждый путь, имя
   записи архива и документ, потому что клиент может быть любой программой.
2. **Защита в несколько слоёв.** Путь проверяется и синтаксически, и после
   разрешения ссылок; размер архива — и по заголовкам, и по фактическим байтам;
   журнал защищён и кодом, и триггерами базы.
3. **Безопасное поведение по умолчанию.** Команда закрыта, пока не открыта
   явно; XML без DTD; распаковка только в новый каталог; перезапись только по
   флагу.
4. **Гонки устранены, а не замаскированы.** Атомарные операции файловой
   системы и базы данных вместо пар «проверить — сделать».
5. **Каждая защита доказана тестом**, воспроизводящим атаку.

Направления развития: шифрование канала TLS, квоты на объём, передача
двоичных файлов, роли пользователей с общими каталогами.
